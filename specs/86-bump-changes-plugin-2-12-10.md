> **For agentic workers:** implement this task-by-task. Steps use checkbox (`- [ ]`) syntax.

**Goal.** Every README generated by parent-poms lists all of a milestone's closed issues,
unlabelled ones included. The site's GitHub report lists them in the same order as the README. A
closed milestone with no issues still gets its section.

**Architecture.** Two configuration changes and no code. `changes.plugin.version` moves to `2.12.10`.
Then the two `github-text-list` executions set `includeEmptyMilestones`: the root `pom.xml`'s
`readme-generation` profile, and `products/pom.xml`'s `product-release-deployment` profile.

**Tech stack.** Maven POM configuration. The proof is a README generated locally, because the
defect this fixes is a silent omission: a green build shows nothing (AC002).

## 1. What 2.12.10 changes for parent-poms

| Fork issue | Effect here | Configuration |
|---|---|---|
| `#36` | An issue with no label is listed, with Type `n/a`. It was dropped before. | None: on by default |
| `#37` | The site's `github-report` orders issues by version descending, then by update date descending, as the README already did. Versions compare as versions, so `3.10.0` sorts above `3.9.2`. | None: on by default |
| `#38` | A closed milestone with no issues renders a `No issues` row. | Opt-in, `includeEmptyMilestones` |

**`#38` is opt-in, and AC004 was added to `#86` for it on 2026-09-30.** The issue's original
criteria predate fork `#38`, so they did not mention the parameter. The DSH PRD gives this issue
the job of turning it on ("parent-poms enables it in step 2").

## 2. Design

### 2.1 The version

`pom.xml`'s `<changes.plugin.version>` moves from `2.12.9` to `2.12.10`. The `pluginManagement`
entry, the `reporting` plugin, and both executions all use the property, so this one line is the
whole bump. `2.12.10` is a release, not a `-SNAPSHOT` (AC001).

### 2.2 `includeEmptyMilestones` on both executions

Both executions are `generate-list-of-issues`, and both bind `github-text-list` with the same
configuration:

- the root `pom.xml`, profile `readme-generation`, activated by `-Ddeployment` at a reactor root
  that holds `src/site/markdown/README.md`;
- `products/pom.xml`, profile `product-release-deployment`, which DSH's release passes through
  `rehearsal-tag` and the release arguments.

`<includeEmptyMilestones>true</includeEmptyMilestones>` is added to both. They share an execution
id, so in a product release, where both profiles are active, Maven merges their configuration.
Setting it in only one would leave the result to inheritance order. The two blocks are already kept
identical, so this keeps that rule.

The parameter is not set at plugin level, in `pluginManagement` or `reporting`. `github-report`
(`GitHubMojo`) has no such parameter, so plugin-level configuration would hand it an unknown one.

### 2.3 Not in scope

- `github-report` cannot render empty milestones. Fork `#38` scoped the parameter to
  `github-text-list`, so AC003 compares issues, and an empty milestone has none.
- Fork `#42`, the APT formatter's NPE. parent-poms generates Markdown only.

## 3. Verification design

All verification is local. Nothing in this section pushes a README or a site.

### 3.1 An unlabelled fixture (AC002)

No closed, milestoned, unlabelled issue exists any more, in parent-poms or in DSH. The six that
existed were labelled as a data fix after `#86` was raised. The proof therefore needs a deliberate
one: **remove the `bug` label from DSH `#146` for the length of one local generation, then put it
back.** `#146` is the only issue in DSH's closed milestone `0.3.2`.

- **Why `#146`.** DSH's README is also where `#38` shows (DSH `0.3.1` is closed and empty), so one
  run covers AC002 and AC004.
- **What else sees the change.** Only a README or site generated from GitHub in that window would
  pick it up. Neither repository has a release or staging run scheduled.
- **The alternative** is opening a throwaway unlabelled issue in a milestone. It would stay in the
  release notes for good, or need deleting.

### 3.2 A DSH README against the local `3.10.0-SNAPSHOT` (AC002, AC004)

1. Run `mvn -B clean install` in parent-poms, so the local repository holds `3.10.0-SNAPSHOT` with
   this change.
2. Make a scratch clone of DSH under the session scratchpad, with `core.longpaths`. Guard the `cd`,
   and point its root `pom.xml`'s parent at `3.10.0-SNAPSHOT`. The real DSH tree is never touched.
3. In the clone, run `mvn -B -N -Ddeployment process-resources`. `readme-generation` writes
   `README.md`.
4. Check that:
   - `#146` is listed under `### Version 0.3.2` with Type `n/a`;
   - `### Version 0.3.1` holds a single `| - | - | No issues | - | - | - |` row;
   - the sections run `0.3.2`, `0.3.1`, `0.3.0`, `0.2.4`, … in descending order.

### 3.3 parent-poms' site report against its README (AC003)

At the parent-poms root, run `mvn -B -N -Ddeployment process-resources` for the README and
`mvn -B -N site` for `target/site/github-report.html`. Then check that:

- both list the same set of issue numbers;
- the site report's version order is descending, `3.9.2` before `3.9.1` before `3.9.0`, and so on.

`3.10.0-SNAPSHOT` above `3.9.x`, the order the issue's comment asks to see, cannot show yet:
`3.10.0-SNAPSHOT` has no closed issues, and both outputs list closed issues only. The fork's
`GitHubIssueComparatorTest` covers that comparison. The 3.10.0 release is its first real
occurrence, and is checked there (task 5).
